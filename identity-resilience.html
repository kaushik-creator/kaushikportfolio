Case study · Identity security

Turning an activity table into an identity graph

Security and backup teams could see that an identity was compromised — but had to read a table, row by row, to find out what it actually touched. I redesigned that table as a graph: the identity at the center, everything it touched plotted around it by type.

RoleUX Designer
ScopeActive Directory, Entra ID, Okta
DomainIdentity security · Enterprise B2B backup & cyber recovery

Status: PRD in review (Rev 0.1). Design explored ahead of and alongside spec — this case study documents that process.

The problem

Detection exists; trusted identity recovery doesn’t

“Detection exists; trusted identity recovery doesn’t. Backup restores systems, not trust.”

What’s wrong with the table

  • Rows hide relationships — nothing shows it’s connected to the identity that did it.

  • You rebuild the shape yourself — tracing how far a compromise spread means reading every row by hand.

  • Every object type looks identical — users, groups, policies, MFA changes, same row, same weight.

  • It falls apart at volume — a hundred events across six object types is just noise during an incident.

That’s the argument for a graph instead of a table: put the compromised identity at the center, plot everything it touched around it by type, and the shape of the attack is visible instead of something you compute.

Existing

Time-ordered table

Every change is a row. Filters find events; they don’t show the path. Multiple entities and activities force responders to rebuild the sequence by hand.

Preferred

Node-based graph

Same audit detail, plotted by object type — nodes for entities, edges for actions — so sequence and blast radius are visible before reading rows.

This screen sits on top of an immutable-snapshot recovery layer — its job is to answer “what changed, when, by whom” before any recovery plan can be trusted.

Reframe

Keep the detail. Show the shape.

The data is relational: one actor, many objects, typed by risk. Tables encode time. Graphs encode relationships. Design question — can both stay true?

Who this is for

Two personas, one investigation artifact

S

Primary user

Security Admin

Gets the flagged identity from a Druva alert or third-party ITDR signal → reads the activity graph to see who did what and how far it spread → hands off to Backup Admin once scope is clear.

B

Primary user

Backup Admin

Picks up from a Druva alert or from what Security Admin found → uses the same graph to find the clean recovery point → restores the identity and reports back.

Both personas converge on the same artifact. Neither can move to recovery without it.

Inspiration

Two references shaped the layout. n8n keeps node types legible because every type carries its own icon and connector style. Wiz’s Security Graph reads left-to-right with no legend at all. Both pointed at the same thing: solve type visually first, or the graph collapses into the same mess as the table it’s replacing.

AI Explorations

Scenarios from the Security Scientist

Scenario 1

One-way timed sequence

Role elevation → new admin → app registration, as a one-way timed sequence. Easy to follow at a glance, but every node carries equal visual weight — nothing signals which step actually matters — and the moment actions branch instead of chaining in one line, it stops working.

Scenario 2

Action-first timeline

MFA changes, guest privilege, long-lived OAuth secrets, laid out as an action-first timeline. Edges carry the color, nodes stay thin, so you see what happened without opening every node. Same ceiling as Scenario 1: nest or multiply the actions and it breaks.

Scenario 3

Clustered bulk deletes

Bulk deletes across users, apps, MFA, secrets, and devices. A hundred deleted devices collapse into one readable cluster instead of a hundred identical rows.

Realisation

Flows aren’t always linear

Flows aren’t always linear. Once an identity’s compromised, it can fan out into many activities at once — a single login can spawn an MFA disable, a role change, and new tokens, all in parallel, not one after another. The graph had to support one origin branching into many forks and stay readable no matter how far it fanned out.

Design system

A working kit for iteration

I built a basic design system to support quick iterations and early explorations — shared with the visual team, engineering, and senior stakeholders so decisions stayed aligned before polish.

The kit covers distinct start/branch node treatments so origin and forks read instantly, action chips that sit right on the swim-lane edge instead of a side legend, nodes that surface type, name, time, and change without a click, and tooltips that carry MITRE technique, severity, and actor on hover.

Design process

Iterations

The spec was specific: identity nodes, action edges, a typed icon per identity type, hover detail, and results that reproduce against the same time window every time. That left three real design problems — keeping six identity types visually distinct without a legend war, keeping the graph legible when one actor fires forty events in ninety seconds (solved by grouping same actor + action + target inside a rolling window), and getting from a flagged node into the recovery flow in one click without losing the context already built.

Iteration 1

Timeline + activity

Once branches grew, finding a specific node in the path got slow, and freeform branches had no stable layout rule for engineering to actually build against. Auto-plotting made it worse — the same events landed in random spots every run, so nothing was reproducible.

Iteration 2

Type swim lanes

Why it worked: Y = identity type, X = time. Empty lanes drop away, so density stays proportional to what actually happened, not to the full taxonomy.

Closing

Learning

  • Invent the system

    First node-based design — no existing interaction model to adapt. Built the design system from scratch, then pressure-tested it with security researchers against privilege escalation, defense evasion, and bulk deletes.

  • Group by relationship

    Not by time. The pattern that came out of this screen is one I’d reach for again outside this specific product.
